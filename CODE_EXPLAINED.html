Gamma Exposure Engine: reading the code

What the project does, how the folders fit together, what each stage puts in and takes out, and the traps a reader should know about before trusting a number.

How to use this

Sections follow the order the pipeline runs in. Every code snippet is copied from the files under src/gamma_exposure_engine/, unedited. Every number in a Sample data box came from actually running the project on the committed demo files (data/raw/, 2 January to 31 January 2024), not from an estimate. Coloured boxes flag design choices, traps, and honest weaknesses.

The process in plain English

The project asks one question: does the shape of SPY option gamma at today's close tell you anything about how SPY behaves tomorrow? It reads two local Parquet files (one minute of SPY price bars per row, one option contract per row), throws away option rows that cannot be used, turns each surviving contract into a single "gamma mass" number, sums those into six daily descriptions of the option surface, reduces the minute bars into seven daily measures of how the market actually moved, pairs day t's option picture with day t+1's market behaviour, and then runs a standard battery of summaries and tests on those pairs.

On the shipped one-month sample the honest answer is: no measurable relationship. The headline rank correlation is 0.030 with a p-value of 0.90 on 20 paired days. The code is built to make that kind of null result visible rather than to hide it.

01The question, and what the data can honestly answer

The research question is written at the top of README.md: what does the observable structure of SPY option gamma tell us about next-day intraday market behaviour?

Two pieces of vocabulary first, because everything else rests on them.

Gamma is the rate at which an option's delta changes when the underlying price moves. Delta is the option's sensitivity to a one dollar move in the underlying; gamma is the sensitivity of that sensitivity. A large gamma means the hedge an option holder needs keeps changing as the price moves, which is why gamma is normally discussed alongside hedging flow.

Open interest is the number of contracts currently outstanding at a given strike and expiry. It is an unsigned count: it says how many contracts exist, not who is long and who is short.

The central honesty constraint

Most published "gamma exposure" work assigns a sign: dealers are assumed short calls and long puts, so their gamma is negative in one region and positive in another, and the sign predicts whether hedging dampens or amplifies moves. This project cannot do that. The raw option schema (listed in docs/reference/offline-data-contract.md) has no account owner, no customer-versus-dealer flag, no trade direction, and no position sign. So the code deliberately computes an unsigned quantity, calls it "gamma mass", and never claims it measures dealer inventory. Rows with negative gamma are rejected as bad input rather than reinterpreted as short positions. The column names carry this: total_open_interest_weighted_gamma, not dealer_gamma_exposure.

Why the project is offline-first

Normal execution reads only three committed files and never opens a network connection. That makes the whole result reproducible on any machine with the repository, which matters for a project whose stated purpose is to be walked through and defended. The ClickHouse database code still exists but is quarantined in one module that the analysis path never imports.

Why the folders are split this way

The split is by stage of the pipeline, not by technical layer. exposure knows about options and nothing about the market's later behaviour; intraday knows about price bars and nothing about options; research knows about neither, only about a table with a factor column and a target column. That means you can read any one folder without holding the others in your head, and a change to how gamma mass is defined cannot accidentally alter how a p-value is computed.

Trap

Two settings (predictive_min_train_size = 20 and regime_lookback_window = 20) are as large as the number of rows the shipped demo data can produce (20). That is not a crash — the modules return empty tables with the correct column names — but it means three of the fifteen output files are empty on a default run, and a reader who does not check run_manifest.json row counts might assume the modules were never wired up. 05Stage 1: loading the raw files — raw_store.py

def _load_required_raw_file(
    file_path: Path,
    dataset_name: str,
    required_columns: tuple[str, ...],
) -> pl.DataFrame:
    """Load one required raw file and validate required columns.

    Raises
    ------
    RuntimeError
        If the file is missing or malformed for offline analysis.
    """

    if not file_path.exists():
        raise RuntimeError(_build_missing_raw_file_message(file_path, dataset_name))

    frame = pl.read_parquet(file_path)
    missing_columns = [
        column_name
        for column_name in required_columns
        if column_name not in frame.columns
    ]
    if missing_columns:
        missing_columns_text = ", ".join(missing_columns)
        raise RuntimeError(
            f"Raw dataset {dataset_name!r} at {file_path} is missing required "
            f"columns: {missing_columns_text}.",
        )

    return frame
In plain words

Open the file if it is there, complain clearly if it is not, and refuse to continue if it is missing a column the rest of the code will need.

What it does

Input: a file path, a friendly dataset name, and the tuple of column names that must exist. Output: a Polars frame with every raw column preserved. Role: the single gate between disk and the pipeline; two public loaders wrap it, one for bars and one for options, each then filtering to the requested inclusive date range.

Why a hard failure instead of a warning

The error message tells the reader exactly what to do next: put files under data/raw or run the refresh command on a machine with database access. A pipeline that silently continues with a missing column produces a table full of nulls that looks like a research result. Failing at the door is cheaper than debugging that later.

06Stage 2: spot close and cleaning — cleaning.py

Before an option row can be used, it needs to know where the underlying closed that day. build_spot_close_frame() supplies that by taking the last bar of each trade date:

def build_spot_close_frame(intraday_bars: pl.DataFrame) -> pl.DataFrame:
    """Reduce minute bars to one daily close row per trade date."""

    dated_bars = intraday_bars.sort(TIMESTAMP_COLUMN).with_columns(
        pl.col(TIMESTAMP_COLUMN).dt.date().alias(TRADE_DATE_COLUMN)
    )
    return (
        dated_bars.group_by(TRADE_DATE_COLUMN)
        .agg(pl.col(CLOSE_COLUMN).last().alias(SPOT_CLOSE_COLUMN))
        .sort(TRADE_DATE_COLUMN)
    )

That frame is joined onto every option row, and then the cleaner runs.

cleaned = cleaned.with_columns(
    # Days to expiry is a simple calendar-day difference.
    (pl.col("expiry_date") - pl.col("trade_date"))
    .dt.total_days()
    .alias("days_to_expiry"),
    # Moneyness is strike scaled by spot and centered at zero for at-the-
    # money contracts.
    ((pl.col("strike_price") / pl.col("spot_close")) - 1.0).alias("moneyness"),
    # This is unsigned market gamma mass, not dealer inventory exposure:
    # OI-weighted gamma = OI * multiplier * spot^2 * gamma.
    (
        pl.col("open_interest")
        * CONTRACT_MULTIPLIER
        * pl.col("spot_close")
        * pl.col("spot_close")
        * pl.col("gamma")
    ).alias("open_interest_weighted_gamma"),
)
In plain words

Throw away option rows that cannot be used, note how many were thrown away and why, and give every surviving row a single number that says how much curvature sits at that strike.

What it does

Input: one row per listed option contract per trade date, with the day's underlying close already attached. Output: the surviving rows plus three new columns — days_to_expiry, moneyness, open_interest_weighted_gamma. Role: everything in aggregation.py consumes this frame and adds no further filtering.

The formula

$$m_{i,t}=OI_{i,t}\cdot M\cdot S_t^{2}\cdot \Gamma_{i,t}$$

$m_{i,t}$ is the gamma mass of contract $i$ on trade date $t$. $OI_{i,t}$ is open interest, a count of outstanding contracts. $M=100$ is the contract multiplier, the number of shares one listed equity option controls. $S_t$ is the underlying close in dollars on day $t$. $\Gamma_{i,t}$ is the option's gamma, the change in delta per one dollar move, in units of one over dollars. The $S_t^{2}$ term converts "delta change per dollar move" into "delta change per proportional move, expressed in dollars", which is what makes the number comparable across price levels. Multiplying $m_{i,t}$ by $0.01$ would express the same curvature for a one percent move.

The formula — moneyness

$$k_{i,t}=\frac{K_i}{S_t}-1$$

$k_{i,t}$ is moneyness, $K_i$ is the strike price in dollars, $S_t$ is the same underlying close. It is zero at the money, positive above spot, negative below. The near-spot band later compares $|k_{i,t}|$ against a threshold.

The put at the same strike carries 51,646 open interest and the same gamma, giving 41,698,232,480.909, which is why the call-versus-put imbalance for 2 January comes out slightly negative.

Whole-sample counts from cleaning_diagnostics.csv: 168,762 rows in, 131,215 rows out. The only exclusion that fires is non-positive open interest, 37,547 rows. Missing essentials, non-positive strike, non-positive spot, expired contracts, invalid option type and negative gamma all count zero. Among the survivors, 24,331 rows have exactly zero gamma and are kept with a flag, and zero rows have a broken bid-ask quote.

Why the exclusion flags are computed in sequence, not in parallel

_build_cleaning_state() builds seven boolean columns where each one is only allowed to be true if none of the earlier ones fired. A row with a null strike is counted once, under "missing essential", and never again. Without that, one bad row could be counted in four different exclusion buckets and the diagnostics table would not add up. The cost is a long chain of nested any_horizontal calls that is tedious to read.

Trap

Zero gamma survives cleaning but invalid quotes also survive, and both are only flagged. That is deliberate: a contract with a wide or crossed quote still has real open interest, and gamma mass does not depend on the quote. The trap is assuming cleaned_options means "trustworthy for pricing". It does not; it means "structurally safe to add up".

The weakness, stated honestly

The spot close used to scale every contract is the last bar in the file, which is 19:59 New York time, not the 16:00 official close. The code has no session filter and no setting for one, so this is not a choice a reader can change from config.toml.

It is not harmless on this data. I compared the 19:59 close against the 15:59 close on all 21 days: they differ on every single day, by up to \$1.61 (0.34 percent, on 30 January), with a mean absolute gap of 0.11 percent. The after-hours session is genuinely active here — 7.5 percent of the month's traded volume comes after 16:00.

What it costs the factors is small but real. Gamma mass carries $S_t^2$, so using the after-hours print rather than the official close multiplies every contract's mass by a factor between 0.9933 and 1.0046. That factor is the same for every contract on a day, so it cancels exactly out of the five ratio factors and shifts only the level factor total_open_interest_weighted_gamma, by at most 0.5 percent. Moneyness and the near-spot band do shift slightly, because those compare each strike against this same spot. The honest summary: the level factor is off by a fraction of a percent, and the classification of a contract as near-spot can flip for strikes sitting right on the 2 percent boundary.

07Stage 3: the six daily gamma factors — aggregation.py

def build_daily_gamma_factors(
    frame: pl.DataFrame,
    near_spot_band: float = DEFAULT_NEAR_SPOT_BAND,
) -> pl.DataFrame:
    daily_totals = _build_daily_totals(frame)
    near_spot = _build_near_spot_share(frame, daily_totals, near_spot_band)
    front_expiry = _build_front_expiry_share(frame, daily_totals)
    largest_node = _build_largest_node_distance(
        frame=frame,
        daily_totals=daily_totals,
    )
    call_put = _build_call_put_imbalance(frame, daily_totals)
    concentration = _build_exposure_concentration_index(frame, daily_totals)

    factors = daily_totals
    factors = factors.join(near_spot, on=TRADE_DATE_COLUMN, how="left")
    factors = factors.join(front_expiry, on=TRADE_DATE_COLUMN, how="left")
    factors = factors.join(largest_node, on=TRADE_DATE_COLUMN, how="left")
    factors = factors.join(call_put, on=TRADE_DATE_COLUMN, how="left")
    factors = factors.join(concentration, on=TRADE_DATE_COLUMN, how="left")

    return factors.sort(TRADE_DATE_COLUMN)
In plain words

Squeeze roughly six thousand option contracts per day down to six numbers that describe the shape of the option surface: how much curvature there is, how close to the current price it sits, how soon it expires, whether it clusters at one strike, and whether it leans toward calls or puts.

What it does

Input: the cleaned contract frame. Output: exactly one row per trade date with six factor columns. Role: this is the left-hand side of the research question. Every day-t variable in the study comes from here.

The six factors, with their formulas

Throughout, $t$ is a trade date, $i$ indexes a contract, $m_{i,t}$ is the contract gamma mass from the previous section, and $G_t=\sum_i m_{i,t}$ is the daily total.

1. Total gamma mass — total_open_interest_weighted_gamma

$$G_t=\sum_{i} m_{i,t}$$

The sum of every surviving contract's gamma mass on day $t$. This is the configured default factor. It is a level, in dollars, of order $10^{12}$.

2. Near-spot share — near_spot_gamma_mass_share

$$N_t=\frac{1}{G_t}\sum_{i:\,|k_{i,t}|\le b} m_{i,t}$$

$k_{i,t}$ is moneyness, $b$ is near_spot_band_width (0.02, meaning plus or minus two percent around spot). $N_t$ is the fraction of the day's curvature sitting close to the current price. When $G_t\le 0$ the code returns zero rather than dividing.

3. Front-expiry share — front_expiry_gamma_mass_share

$$F_t=\frac{1}{G_t}\sum_{i:\,T_i=\min_j T_j} m_{i,t}$$

$T_i$ is contract $i$'s expiry date, and the minimum is taken over the contracts present on day $t$. $F_t$ is the fraction of curvature in the nearest expiry.

4. Distance to the largest node — largest_gamma_mass_strike_distance

$$D_t=\big|k_{K^{\ast}_t,\,t}\big|,\qquad K^{\ast}_t=\arg\max_{K}\ \sum_{i:\,K_i=K} m_{i,t}$$

Contracts are first summed to strike level, the strike $K^{\ast}_t$ with the largest total is selected, and $D_t$ is how far that strike sits from spot in proportional terms. Ties are broken by the smaller distance first, then the lower strike, so the choice is deterministic. Strikes with zero mass are excluded before the search.

5. Call-versus-put imbalance — call_put_gamma_mass_imbalance

$$I_t=\frac{C_t-P_t}{G_t}$$

$C_t$ is the gamma mass summed over calls only, $P_t$ over puts only, and $G_t=C_t+P_t$. $I_t$ lies between $-1$ and $+1$: positive means the curvature sits more in calls. This is a composition measure, not a position sign.

6. Concentration index — gamma_mass_concentration_index

$$H_t=\sum_{(K,T)}\left(\frac{m_{K,T,t}}{G_t}\right)^{2}$$

This is the Herfindahl-Hirschman index, a standard concentration measure. $m_{K,T,t}$ is the gamma mass summed over all contracts sharing strike $K$ and expiry $T$ on day $t$. $H_t$ is near zero when curvature is spread evenly over many strike-expiry pairs and approaches 1 when it sits almost entirely in one. The name comes from industrial economics, where the same sum of squared market shares measures how concentrated an industry is.

Why every factor except the first is a ratio

Total gamma mass grows mechanically with the price level, because of the $S_t^2$ term, and with the size of the option market. The five ratios divide that out, so they describe shape rather than size. That matters when the sample is short: a level factor over one month is close to a slow trend, and a rank correlation against another trending series will pick up the trend rather than the relationship.

Trap

"Front expiry" on this data means "expires today". SPY lists same-day expiries, the cleaner only drops contracts whose expiry is before the trade date, so the nearest expiry on day $t$ is almost always day $t$ itself. I checked this numerically: the front-expiry share equals the share of gamma mass in same-day expiries on every day of the sample, and averages 0.152. Those contracts stop existing at the day-$t$ close, so about fifteen percent of the day-$t$ gamma picture cannot influence day $t+1$ by construction.

08Stage 4: the seven daily response metrics — metrics.py

def _build_daily_bar_metrics(minute_bars: pl.DataFrame) -> pl.DataFrame:
    """Compute realized variance and basic daily summary metrics."""

    daily_bars = minute_bars.with_columns(
        pl.col(CLOSE_COLUMN).log().alias("_log_close")
    )
    daily_bars = daily_bars.with_columns(
        (pl.col("_log_close") - pl.col("_log_close").shift(1))
        .over(TRADE_DATE_COLUMN)
        .alias(LOG_RETURN_COLUMN)
    )
    daily_metrics = daily_bars.group_by(TRADE_DATE_COLUMN).agg(
        pl.col(LOG_RETURN_COLUMN).pow(2).sum().alias(REALIZED_VARIANCE_COLUMN),
        ((pl.col(CLOSE_COLUMN).last() / pl.col(OPEN_COLUMN).first()) - 1.0)
        .abs()
        .alias(OPEN_TO_CLOSE_ABS_RETURN_COLUMN),
        pl.col(CLOSE_COLUMN).last().alias(CLOSE_PRICE_COLUMN),
        pl.col(VOLUME_COLUMN).sum().alias(TOTAL_VOLUME_COLUMN),
    )
    return daily_metrics.sort(TRADE_DATE_COLUMN)
In plain words

Turn about eight hundred price bars per day into a handful of numbers that describe how much the market actually moved that day, how much it traded, and how close it finished to yesterday's biggest gamma strikes.

What it does

Input: minute bars for the whole window. Output: one row per trade date with seven columns. Role: this is the right-hand side of the research question, the thing the gamma factors are tested against.

The formula — realized variance

$$RV_t=\sum_{k=2}^{n_t}\big(\ln C_{t,k}-\ln C_{t,k-1}\big)^{2}$$

$C_{t,k}$ is the closing price of the $k$-th minute bar on day $t$, and $n_t$ is how many bars that day has. The sum starts at $k=2$ because the first bar of a day has no predecessor inside that day. This is the standard realized-variance estimator: add up squared minute-by-minute log returns. It is not annualized, so a value like $4.3\times10^{-5}$ is a daily variance, and its square root $6.6\times10^{-3}$ is a daily standard deviation of about 0.66 percent.

The formula — abnormal volume score

$$A_t=\frac{V_t}{\hat V_t},\qquad \hat V_t=\sum_{u}\ \frac{1}{w}\sum_{j=1}^{w} v_{t-j,\,u}$$

$V_t$ is total traded volume on day $t$. $u$ indexes minute-of-day buckets (09:31, 09:32, and so on). $v_{s,u}$ is the volume traded in bucket $u$ on day $s$. $w$ is abnormal_volume_window, 20 trade dates. So the expected volume $\hat V_t$ is built minute by minute from the previous $w$ days only, and $A_t$ above 1 means the day traded more than its own recent norm. Days with no prior history get $A_t=0$ by explicit contract.

The formula — pinning distance

$$\Pi_{t+1}=\min_{K\in\mathcal{K}_t}\ \frac{\big|C_{t+1}-K\big|}{C_{t+1}}$$

$\mathcal{K}_t$ is the set of the five strikes with the most gamma mass on day $t$ (pinning_candidate_count). $C_{t+1}$ is the closing price on the next trade date. $\Pi_{t+1}$ is how close the market finished to the nearest of yesterday's big gamma strikes, as a fraction of the price. A small value is what "pinning" would look like. Dividing by $C_{t+1}$ makes the number comparable across price levels.

Why the volume baseline is built minute by minute

Intraday volume has a strong U-shape: the open and the close trade far more than the middle of the day. If a day is missing its last hour of bars, its total volume drops sharply for a reason that has nothing to do with market interest. Comparing 10:31 against past 10:31s and then adding those expectations up removes that shape from the comparison. The rolling mean is shifted forward one day inside each minute bucket, so day $t$ never sees its own volume.

Trap

The rolling mean uses min_samples=1, so on day two of the sample the "20-day baseline" is a single prior day. On this 21-day dataset the window never actually fills. Every abnormal-volume score in the shipped outputs is therefore computed against a shorter and noisier baseline than the setting suggests.

The weakness, stated honestly

Realized variance is summed over all the bars in the file, which run 04:00 to 19:59 New York time, not the 09:30 to 16:00 regular session. Pre-market minutes are thin, and a squared return from a stale pre-market print enters the sum with the same weight as a real one. The same applies to open_to_close_abs_return, whose "open" is the 04:00 bar. There is no session filter in the code and no configuration option for one.

I recomputed realized variance over the 09:30 to 16:00 session only and compared. The extended-hours number is larger every day, with a median ratio of 1.57 and a mean of 2.30. The two series are far from interchangeable: their rank correlation across the 21 days is 0.61, and on 2 January the extended-hours figure is 9.6 times the regular-session one. So the headline target is not the realized variance a data vendor would quote, and the choice of session materially changes which days count as the volatile ones.

def _build_exposure_calendar(exposures: pl.DataFrame) -> pl.DataFrame:
    """Sort exposures and attach the next observed exposure date."""

    ordered_exposures = exposures.sort(TRADE_DATE_COLUMN)
    return ordered_exposures.with_columns(
        # The next exposure date defines the only allowed response match.
        pl.col(TRADE_DATE_COLUMN).shift(-1).alias(NEXT_EXPOSURE_DATE_COLUMN)
    )
In plain words

For each day, look up what the option surface looked like at that day's close, then attach what the market did on the following trading day. Keep the date of that following day in the table so anyone can check the pairing by eye.

What it does

Input: the daily factor frame and the daily response frame, each keyed by trade date. Output: one row per exposure date that has a following exposure date, carrying the six factors, the matched response_trade_date, and seven response columns renamed with a next_day_ prefix. Role: the only place in the project where a day-t variable meets a day-t+1 variable. Every research module downstream reads this one table.

Whole-sample fact: 21 exposure dates in, 20 rows out. The last exposure date, 31 January, is dropped because nothing follows it. The first response date, 2 January, is never used as a response for the same reason in reverse — which is convenient, because that is exactly the row whose abnormal-volume score is the placeholder zero.

Why the match is "next observed exposure date" and not "next calendar day"

Adding one day to a Friday gives a Saturday, which has no data, and a naive join would then silently drop every Friday from the sample. Shifting the exposure calendar by one position instead means the next row is whatever the next trading day actually was. The extra strictness is that the matched date must be the next exposure date: if the option file has a day the bar file does not, the pair is dropped rather than quietly reaching two days forward.

Where look-ahead is prevented

Three separate places. First, here: the response is strictly the following day, and response_trade_date is kept in the output so the claim is auditable. Second, in the abnormal-volume baseline, where the rolling mean is shifted one day forward inside each minute bucket. Third, in the walk-forward forecasts, where the model for row $j$ is fitted on slice(0, j) and predicts row $j$. I checked all three against the actual data and they hold.

descriptive.build_quantile_summary — sort into buckets, average the target

def _build_quantile_buckets(row_count: int, quantiles: int) -> list[int]:
    """Assign each row to a deterministic integer bucket."""

    bucket_labels: list[int] = []
    for row_index in range(row_count):
        # Scale the zero-based row index into the integer bucket range
        # ``[0, quantiles - 1]`` without relying on percentile interpolation.
        bucket_index = (row_index * quantiles) // row_count
        bucket_labels.append(bucket_index)
    return bucket_labels
The formula

$$\text{bucket}(j)=\left\lfloor \frac{j\,q}{n}\right\rfloor,\qquad j=0,1,\dots,n-1$$

$j$ is the row's position after sorting by the factor, $n$ is the number of rows, $q$ is quantile_count. The floor brackets mean "round down to a whole number". With $n=20$ and $q=5$ this gives five buckets of exactly four rows.

Why rank position rather than percentile cut points

Percentile-based bucketing has to decide what to do when many rows share a value, and different libraries decide differently, which makes bucket sizes wobble. Slicing the sorted list by position always produces bucket sizes that differ by at most one, which is what the bootstrap needs to be comparable across resamples. The price is that the bucket edges are not round numbers of the factor.

bootstrap.build_quantile_summary_with_ci — how wide is that number

The formula

$$\big[\hat\mu^{(\alpha/2)}_{b},\ \hat\mu^{(1-\alpha/2)}_{b}\big],\qquad \alpha=1-c$$

$c$ is bootstrap_confidence_level, 0.95, so $\alpha=0.05$. The procedure draws $n$ whole rows with replacement from the aligned table, re-sorts them into buckets, records each bucket's target mean, and repeats 1,000 times. $\hat\mu^{(p)}_{b}$ is the $p$-th percentile of the recorded means for bucket $b$. Rows are resampled whole, not column by column, so the pairing between factor and target is never broken.

Why the confidence bands are the same on every run

The generator is seeded: random_seed: int = 42 is a default argument of build_quantile_summary_with_ci(), and nothing in the pipeline overrides it. That is why re-running the pipeline reproduces ci_lower and ci_upper to the last decimal, which is how the bands in the box above were checked. The seed is the one tunable value that lives in the source rather than in config.toml; changing it would move every published interval slightly, which is a good reason to leave it pinned.

The weakness, stated honestly

The resample treats the 20 days as independent draws. Realized variance is strongly autocorrelated — a volatile day is usually followed by another one — so an independent-row bootstrap understates how uncertain these means really are. A block bootstrap, which resamples runs of consecutive days, would give wider and more honest bands. The bands shown above are therefore the optimistic version, and they already overlap completely.

statistical_tests.build_statistical_test_summary — two formal tests

The formulas

Spearman rank correlation:

$$\rho=\mathrm{corr}\big(\mathrm{rank}(x),\ \mathrm{rank}(y)\big)$$

Kruskal-Wallis statistic:

$$H=\frac{12}{n(n+1)}\sum_{g=1}^{q}\frac{R_g^{2}}{n_g}-3(n+1)$$

For Spearman, $x$ is the factor and $y$ the target, and $\mathrm{rank}$ replaces each value by its position in the sorted order, so the measure detects any consistently increasing or decreasing relationship rather than only a straight-line one. $\rho$ runs from $-1$ to $+1$. For Kruskal-Wallis, $n$ is the total sample size, $q$ the number of buckets, $n_g$ the size of bucket $g$, and $R_g$ the sum of the overall ranks of the target values falling in bucket $g$. $H$ is large when the buckets sit at different places in the overall ranking. Both are computed by SciPy; the formulas above are what SciPy implements.

Sample data

spearman_rank_correlation   0.030075        0.899837   20

A p-value is the probability of seeing a statistic at least this extreme if there were genuinely no relationship. At 0.90 and 0.31, neither test finds anything. This is the headline result of the project on the shipped sample.

predictive — walk-forward forecasts

    for prediction_index in range(min_train_size, ordered_frame.height):
        # Train on rows strictly before the prediction row to keep the

        train_frame = ordered_frame.slice(0, prediction_index)

The formula — what the ridge model minimises

$$\hat\beta=\arg\min_{\beta}\ \sum_{s=1}^{j}\big(y_s-\beta_0-\beta_1 x_s\big)^{2}+\lambda\beta_1^{2}$$

$x_s$ is the factor on training row $s$, $y_s$ the target, $j$ the index of the row being predicted, $\beta_0$ the intercept and $\beta_1$ the slope. $\lambda$ is the penalty strength, chosen from ridge_alpha_candidates by cross-validation inside the training window whenever at least two folds fit, and otherwise fixed at the first candidate. The extra $\lambda\beta_1^{2}$ term shrinks the slope toward zero, which is what stops a handful of early observations from producing a wild fit. Plain least squares is the same expression with $\lambda=0$.

The formula — the two error measures

$$\mathrm{MAE}=\frac{1}{P}\sum_{p=1}^{P}\big|y_p-\hat y_p\big|,\qquad \mathrm{RMSE}=\sqrt{\frac{1}{P}\sum_{p=1}^{P}\big(y_p-\hat y_p\big)^{2}}$$

$P$ is the number of out-of-sample predictions, $y_p$ the realized target and $\hat y_p$ the forecast. MAE is the mean absolute error, the average size of a miss. RMSE is the root mean squared error, which punishes big misses more heavily. Both are reported in the units of the target, so for realized variance they are also of order $10^{-5}$.

Why there is a naive baseline at all

The third model simply predicts that tomorrow's realized variance equals the value from the previous row. Volatility is persistent, so this baseline is genuinely hard to beat, and a model that cannot beat it has demonstrated nothing regardless of how good its error numbers look on their own. All three models are scored on exactly the same prediction dates so the comparison is fair.

Trap

When the training window is too short to cross-validate, the fallback penalty is alpha_candidates[0], which with the configured list is 0.01 — the weakest penalty. That is exactly backwards from what regularisation is for: the smallest training windows are the ones that most need shrinkage. It only bites in the first few walk-forward steps, and on the default configuration it never runs at all, but it is worth knowing before changing predictive_min_train_size.

13Fixes applied

Bug found and fixed: minute-of-day was wrapping around

In intraday/metrics.py, _build_minute_bars() computed the minute-of-day bucket as:

(pl.col(TIMESTAMP_COLUMN).dt.hour() * 60 + pl.col(TIMESTAMP_COLUMN).dt.minute())
.cast(pl.Int32)

Polars returns Int8 for both dt.hour() and dt.minute(), and Int8 arithmetic wraps around at 127. The multiplication happened before the cast, so hour * 60 overflowed for every hour from 3 onward. The result was not a minute of the day at all: 04:00 became −16, 09:00 became 28, 15:30 became −94, 19:30 became −110. Worse, unrelated clock minutes collided into the same bucket — 04:44 and 09:00 both mapped to 28. The 960 real minute buckets in the file collapsed into 256.

The fix casts each part to Int32 before the arithmetic, adds a named constant for the 60, and explains the reason in a comment:

(
    pl.col(TIMESTAMP_COLUMN).dt.hour().cast(pl.Int32) * MINUTES_PER_HOUR
    + pl.col(TIMESTAMP_COLUMN).dt.minute().cast(pl.Int32)
).alias(MINUTE_OF_DAY_COLUMN)

Blast radius: minute_of_day is used in exactly one place, the abnormal-volume baseline. Because the sum of trailing means is linear, merging buckets mostly cancels out when every day has the same set of minutes, so the numerical change on this dataset is small: the largest change to any abnormal_volume_score is 0.0049, on 3 January, which moved from 0.913192 to 0.918058. The column was still wrong in principle, would drift further on data with more missing bars, and would have been badly wrong for anyone plotting an intraday volume profile from that column.

Verification: after the fix, minute_of_day has 960 distinct values running 240 to 1199 (04:00 to 19:59), which is exactly right. A regression test was added at tests/intraday/test_metrics.py::test_build_minute_bars_keeps_afternoon_minutes_distinct, asserting that 04:44, 09:00, 15:30 and 19:59 map to 284, 540, 930 and 1199.

Bug found and fixed: unusable rows were being filed into a real bucket

build_quantile_summary() in descriptive.py was the only public research helper with no cleaning pass. Its four siblings — statistical_tests, multi_factor, _build_spearman_summary_row and the predictive helpers — all begin by dropping rows where either column is null or non-finite. This one sorted the raw frame straight into buckets.

Polars sorts nulls first and NaN last. Because buckets are assigned by rank position, that put every row with a missing factor into bucket 0 — the "lowest gamma exposure" bucket — and every NaN-factor row into the top bucket. The bucket mean then reported those rows as though they were real readings. Three concrete symptoms, each reproduced on a small frame:

  • A phantom bucket. Two rows with a null factor and a target of 50.0 produced bucket 0, target_mean 50.0, observation_count 2. The lowest-exposure bucket was pure missingness.
  • A count that did not match its own mean. observation_count uses pl.len(), which counts every row in the bucket, while .mean() skips nulls. A bucket reported observation_count = 2 beside target_mean = null — two observations behind a mean that no row contributed to.
  • Two report tables disagreeing. On the same eight-row input, statistical_tests.csv reported sample_size 6 while quantile_summary.csv accounted for all eight rows.

Worse, the null mean crashed the bootstrap. bootstrap.py wraps each resampled bucket mean in float(...) with a not-a-number default, but the default only covers a missing key, not a key holding None:

float(resampled_means_by_bucket.get(bucket_label, float("nan")))
# TypeError: float() argument must be a string or a real number, not 'NoneType'

The fix applies the same pairwise cleaning the siblings use, before sorting:

clean_frame = frame.drop_nulls([factor_name, target_name]).filter(
    pl.col(factor_name).is_finite(),
    pl.col(target_name).is_finite(),
)

Blast radius: none on the shipped demo run. The alignment step drops the only day carrying missing values, so the 20-row research dataset has no nulls and no NaN in any column. I confirmed the fix leaves every output table numerically identical. The bug was latent, waiting for a longer or gappier sample — where it would have shown up first as a hard crash, and second as a fabricated bottom bucket.

Verification: two regression tests were added to tests/research/test_descriptive.py, one asserting that null and NaN rows never reach a bucket, one asserting that observation_count matches the rows behind target_mean. The suite goes from 74 tests at the start of this review to 77 passing, 1 skipped.

Two more genuine defects, found but deliberately left alone

I am flagging these rather than fixing them, because fixing either one means deciding what the author intended, and both sit outside the path that produces the shipped tables.

1. build_prediction_intervals() in predictive.py looks ahead. It builds the residual pool from the entire evaluation window and then draws from that same pool for every row, so the interval on the first out-of-sample day is informed by the error made on the last day. The module docstring says these helpers "are intentionally walk-forward and trade-date sorted so they remain safe for time-series evaluation"; this one function is not. On a test series whose residuals are small for twenty days and then large for twenty days, the first row's interval came out roughly 800 times wider than an expanding-window interval would be. The function is exported and tested but never called by offline_pipeline.py, so no shipped table is affected. A correct version would grow the residual pool one row at a time.

2. load_settings(project_root=...) does not relocate the config or the environment file. The three path arguments are independent, so passing only project_root gives you an AppSettings whose outputs_dir points at the new root while every configured value still comes from the real repository — and it silently reads the developer's real .env. Every existing test passes all three paths together, so nothing exercises it. Deriving the two file paths from the resolved root when they are not given explicitly would close it.

The pipeline is not bit-for-bit reproducible

Running gex run-offline-analysis twice on identical code and identical input does not produce identical CSV files. Polars sums grouped floating-point columns across threads, and the order of that reduction varies between runs, so the last one or two digits move. I measured the drift at about $4\times10^{-14}$ relative on gamma_factors.csv and $1\times10^{-15}$ on intraday_metrics.csv.

This is far below anything the analysis depends on, and every figure quoted on this page is rounded well inside it. It is worth knowing anyway: comparing two runs with cmp or a checksum will report a difference that is not a change, so any regression check on these outputs has to compare with a numerical tolerance rather than byte-for-byte.

Also worth knowing

The committed output tables under outputs/ and blog/data/ were generated before this fix, so their abnormal_volume_score column carries the old values. They were left alone deliberately, since regenerating them is a separate decision. Rerunning gex run-offline-analysis reproduces the corrected numbers.

Considered and deliberately not changed

Four things look like defects but are research decisions that would change every published number in the project, so they are documented above rather than silently altered: the extended-hours session used for realized variance, the inclusion of same-day expiries in the day-t gamma picture, the full-sample median used as the regime cut point, and the independent-row bootstrap on autocorrelated data. Three smaller ones: the ClickHouse client in raw_cache_builder.py is never explicitly closed (harmless in a one-shot command that then exits), predictive.py keeps an unused alias add_naive_volatility_baseline that only forwards to the current function, and the maximum cross-validation fold count in predictive.py is the bare number 5 rather than a named constant or a configuration entry.

16Gotchas and traps

Idiom or settingWhat it doesThe trap
dt.hour() in PolarsReturns the local hour of a timezone-aware timestampThe dtype is Int8. Any arithmetic that can exceed 127 wraps around silently. This is the bug fixed in section 13. Cast before you multiply.
expr.over("trade_date")Evaluates the whole expression inside each groupIt respects the frame's existing row order, so it is only correct if you sorted first. Both uses here do sort first; I verified the resulting values are past-only.

17Limitations, stated honestly

  • No position sign exists in the data. Everything here is unsigned gamma mass. Nothing in this repository can distinguish a market where dealers are long gamma from one where they are short, and the sign is the whole mechanism behind the usual gamma story.
  • Twenty paired observations. One month of one symbol. Five quantile buckets of four days each. Nothing in this sample could reach statistical significance for an effect of a realistic size, so "no relationship found" here is close to uninformative about whether a relationship exists.
  • Three of fifteen output tables are empty by default, because two window settings are as long as the sample. The code is correct; the demonstration is short.
  • Association only. Even with a longer sample, this design would show that two things move together, not that one causes the other.
  • Realized variance is measured over extended hours, which is not the standard definition and would not match a vendor's daily realized-variance series. Measured properly over 09:30 to 16:00 it is smaller every day — median ratio 1.57 — and the two versions only rank days 0.61 alike, so the choice of session changes which days are the volatile ones.
  • The spot close is the 19:59 print, not the 16:00 official close. It differs from the regular-session close on all 21 days, by up to 0.34 per cent. The five ratio factors are unaffected because the scaling cancels, but the level factor moves by up to half a per cent and near-spot classification can flip for strikes sitting on the band edge.
  • The confidence bands are optimistic, because the bootstrap treats consecutive trading days as independent.
  • The regime threshold uses the full sample, which is fine for a descriptive split and not fine for anything described as real-time.
  • Cleaning conventions move the answer. Rows with non-positive open interest are 22 percent of the raw file, and same-day expiries are 15 percent of daily mass. Different, equally defensible choices would produce different factors.
