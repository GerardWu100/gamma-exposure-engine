Gamma Exposure Engine: reading the code

What the project does, how its folders fit together, what each stage takes in and returns, and what to check before trusting a number.

How to use this

The sections follow the pipeline from start to finish. Every code snippet is copied unchanged from src/gamma_exposure_engine/. Every number in a Sample data box comes from running the project on the committed demo files (data/raw/, 2 January to 31 January 2024). Coloured boxes mark design choices, traps, and weaknesses.

The process in plain English

The project asks one question: does the shape of SPY option gamma at today's close tell us anything about how SPY behaves tomorrow? It reads two local Parquet files, a column-based file format: one row per minute of SPY price bars and one row per option contract. It removes unusable option rows, gives each remaining contract one "gamma mass" value, and sums those values into six daily descriptions of the option surface, meaning the pattern of gamma across strikes and expiries. It also turns the minute bars into seven daily measures of market behaviour. Finally, it pairs day t's option data with day t+1's market data and tests the pairs.

For the shipped one-month sample, the answer is no measurable relationship. The headline rank correlation, which compares the order of two series, is 0.030. Its p-value, the probability of seeing a result this extreme if there were no relationship, is 0.90 across 20 paired days. The code reports that null result instead of hiding it.

01The question, and what the data can honestly answer

The research question appears at the top of README.md: what does the observable structure of SPY option gamma tell us about next-day intraday market behaviour?

Two terms matter first.

Gamma is how quickly an option's delta changes when the underlying price moves. Delta is the option's sensitivity to a one-dollar move in the underlying; gamma is the sensitivity of delta itself. With high gamma, the hedge an option holder needs changes quickly as the price moves, so gamma is often discussed with hedging flow.

Open interest is the number of contracts outstanding at a given strike and expiry. It is unsigned: it counts contracts but does not show who is long or short.

The central honesty constraint

Many published "gamma exposure" studies assign a sign by assuming dealers are short calls and long puts. That sign is then used to say whether hedging dampens or amplifies moves. This project cannot do that. The raw option schema (listed in docs/reference/offline-data-contract.md) has no account owner, customer-versus-dealer flag, trade direction, or position sign. The code therefore computes an unsigned quantity called "gamma mass" and does not claim to measure dealer inventory. Negative gamma is rejected as bad input, not treated as a short position. The column names make this explicit: total_open_interest_weighted_gamma, not dealer_gamma_exposure.

Why the project is offline-first

A normal run reads three committed files and never opens a network connection. Anyone with the repository can therefore reproduce the result. The ClickHouse database code remains available for refreshes, but the analysis path never imports it.

05Stage 1: loading the raw files — raw_store.py

def _load_required_raw_file(
    file_path: Path,
    dataset_name: str,
    required_columns: tuple[str, ...],
) -> pl.DataFrame:
    """Load one required raw file and validate required columns.

    Raises
    ------
    RuntimeError
        If the file is missing or malformed for offline analysis.
    """

    if not file_path.exists():
        raise RuntimeError(_build_missing_raw_file_message(file_path, dataset_name))

    frame = pl.read_parquet(file_path)
    missing_columns = [
        column_name
        for column_name in required_columns
        if column_name not in frame.columns
    ]
    if missing_columns:
        missing_columns_text = ", ".join(missing_columns)
        raise RuntimeError(
            f"Raw dataset {dataset_name!r} at {file_path} is missing required "
            f"columns: {missing_columns_text}.",
        )

    return frame
In plain words

Open the file, report a clear error if it is missing, and stop if a required column is absent.

What it does

Input: a file path, a dataset name, and the required column names. Output: a Polars DataFrame, or table, containing every raw column. Role: the only gate between disk and the pipeline. Two public loaders use it, one for bars and one for options, then filter to the requested inclusive date range.

06Stage 2: spot close and cleaning — cleaning.py

Each option row needs the underlying's close for that day. build_spot_close_frame() supplies it by taking the last bar for each trade date:

def build_spot_close_frame(intraday_bars: pl.DataFrame) -> pl.DataFrame:
    """Reduce minute bars to one daily close row per trade date."""

    dated_bars = intraday_bars.sort(TIMESTAMP_COLUMN).with_columns(
        pl.col(TIMESTAMP_COLUMN).dt.date().alias(TRADE_DATE_COLUMN)
    )
    return (
        dated_bars.group_by(TRADE_DATE_COLUMN)
        .agg(pl.col(CLOSE_COLUMN).last().alias(SPOT_CLOSE_COLUMN))
        .sort(TRADE_DATE_COLUMN)
    )

The pipeline joins that frame to every option row before cleaning.

cleaned = cleaned.with_columns(
    # Days to expiry is a simple calendar-day difference.
    (pl.col("expiry_date") - pl.col("trade_date"))
    .dt.total_days()
    .alias("days_to_expiry"),
    # Moneyness is strike scaled by spot and centered at zero for at-the-
    # money contracts.
    ((pl.col("strike_price") / pl.col("spot_close")) - 1.0).alias("moneyness"),
    # This is unsigned market gamma mass, not dealer inventory exposure:
    # OI-weighted gamma = OI * multiplier * spot^2 * gamma.
    (
        pl.col("open_interest")
        * CONTRACT_MULTIPLIER
        * pl.col("spot_close")
        * pl.col("spot_close")
        * pl.col("gamma")
    ).alias("open_interest_weighted_gamma"),
)
In plain words

Remove unusable option rows, record why each one was removed, and give each remaining row one number for the curvature at its strike.

What it does

Input: one row per listed option contract and trade date, with that day's underlying close attached. Output: the surviving rows plus days_to_expiry, moneyness, and open_interest_weighted_gamma. Role: aggregation.py consumes this frame without further filtering.

The formula

$$m_{i,t}=OI_{i,t}\cdot M\cdot S_t^{2}\cdot \Gamma_{i,t}$$

$m_{i,t}$ is the gamma mass of contract $i$ on trade date $t$. $OI_{i,t}$ is open interest, the number of outstanding contracts. $M=100$ is the contract multiplier: one listed equity option controls 100 shares. $S_t$ is the underlying close in dollars on day $t$. $\Gamma_{i,t}$ is gamma, the change in delta per one-dollar move, measured in inverse dollars. The $S_t^{2}$ term converts a change per dollar into a change per proportional price move, expressed in dollars, making the result comparable across price levels. Multiplying $m_{i,t}$ by $0.01$ gives the same curvature for a one-percent move.

The formula — moneyness

$$k_{i,t}=\frac{K_i}{S_t}-1$$

$k_{i,t}$ is moneyness. $K_i$ is the strike price in dollars, and $S_t$ is the same underlying close. Moneyness is zero at the money, positive above spot, and negative below. The near-spot band later compares $|k_{i,t}|$ with a threshold.

The put at the same strike has 51,646 open interest and the same gamma, giving 41,698,232,480.909. That is why the call-versus-put imbalance for 2 January is slightly negative.

Across the full sample, cleaning_diagnostics.csv records 168,762 input rows and 131,215 remaining rows. The only exclusion is non-positive open interest, affecting 37,547 rows. Missing essentials, non-positive strike, non-positive spot, expired contracts, invalid option type, and negative gamma each affect zero rows. Among the remaining rows, 24,331 have exactly zero gamma and are kept with a flag; zero rows have a broken bid-ask quote.

Why the exclusion flags are computed in sequence, not in parallel

_build_cleaning_state() builds seven true/false columns in order. Each flag can be true only when earlier flags are false. A row with a null strike is therefore counted once under "missing essential". Without this rule, one bad row could appear in four exclusion buckets and the diagnostics would not add up. The trade-off is a long chain of nested any_horizontal calls.

Trap

Zero gamma and invalid quotes both survive cleaning with flags. That is deliberate: a wide or crossed quote still has open interest, and gamma mass does not use the quote. cleaned_options therefore means "safe to aggregate", not "trustworthy for pricing".

The weakness, stated honestly

The spot close used to scale each contract is the last bar in the file: 19:59 New York time, not the 16:00 official close. The code has no session filter or configuration setting for one, so config.toml cannot change this.

This matters on the sample. The 19:59 and 15:59 closes differ on every single day, by up to \$1.61 (0.34 percent, on 30 January), with a mean absolute gap of 0.11 percent. After-hours trading accounts for 7.5 percent of the month's volume.

Gamma mass includes $S_t^2$, so the after-hours print multiplies every contract's mass by 0.9933 to 1.0046. The factor is the same for every contract on a day, so it cancels from the five ratio factors and changes only total_open_interest_weighted_gamma, by at most 0.5 percent. Moneyness and the near-spot band also move slightly because they compare each strike with this spot. A strike at the 2 percent boundary can change classification.

07Stage 3: the six daily gamma factors — aggregation.py

def build_daily_gamma_factors(
    frame: pl.DataFrame,
    near_spot_band: float = DEFAULT_NEAR_SPOT_BAND,
) -> pl.DataFrame:
    daily_totals = _build_daily_totals(frame)
    near_spot = _build_near_spot_share(frame, daily_totals, near_spot_band)
    front_expiry = _build_front_expiry_share(frame, daily_totals)
    largest_node = _build_largest_node_distance(
        frame=frame,
        daily_totals=daily_totals,
    )
    call_put = _build_call_put_imbalance(frame, daily_totals)
    concentration = _build_exposure_concentration_index(frame, daily_totals)

    factors = daily_totals
    factors = factors.join(near_spot, on=TRADE_DATE_COLUMN, how="left")
    factors = factors.join(front_expiry, on=TRADE_DATE_COLUMN, how="left")
    factors = factors.join(largest_node, on=TRADE_DATE_COLUMN, how="left")
    factors = factors.join(call_put, on=TRADE_DATE_COLUMN, how="left")
    factors = factors.join(concentration, on=TRADE_DATE_COLUMN, how="left")

    return factors.sort(TRADE_DATE_COLUMN)
In plain words

Reduce roughly six thousand option contracts per day to six numbers: total curvature, distance from the current price, time to expiry, concentration at one strike, and the call-versus-put balance.

What it does

Input: the cleaned contract table. Output: one row per trade date with six factor columns. Role: this is the input side of the research question. Every day-t variable comes from here.

The six factors, with their formulas

Here, $t$ is a trade date, $i$ identifies a contract, $m_{i,t}$ is its gamma mass, and $G_t=\sum_i m_{i,t}$ is the daily total.

1. Total gamma mass — total_open_interest_weighted_gamma

$$G_t=\sum_{i} m_{i,t}$$

The sum of gamma mass across all surviving contracts on day $t$. This is the configured default factor. It is a dollar level of order $10^{12}$.

2. Near-spot share — near_spot_gamma_mass_share

$$N_t=\frac{1}{G_t}\sum_{i:\,|k_{i,t}|\le b} m_{i,t}$$

$k_{i,t}$ is moneyness. $b$ is near_spot_band_width (0.02, or plus or minus two percent around spot). $N_t$ is the fraction of the day's curvature near the current price. When $G_t\le 0$, the code returns zero instead of dividing.

3. Front-expiry share — front_expiry_gamma_mass_share

$$F_t=\frac{1}{G_t}\sum_{i:\,T_i=\min_j T_j} m_{i,t}$$

$T_i$ is contract $i$'s expiry date. The minimum is taken over contracts present on day $t$. $F_t$ is the fraction of curvature in the nearest expiry.

4. Distance to the largest node — largest_gamma_mass_strike_distance

$$D_t=\big|k_{K^{\ast}_t,\,t}\big|,\qquad K^{\ast}_t=\arg\max_{K}\ \sum_{i:\,K_i=K} m_{i,t}$$

The code first sums contracts at each strike, selects the strike $K^{\ast}_t$ with the largest total, and measures its proportional distance from spot as $D_t$. Ties use the smaller distance, then the lower strike, so the result is deterministic. Strikes with zero mass are excluded.

5. Call-versus-put imbalance — call_put_gamma_mass_imbalance

$$I_t=\frac{C_t-P_t}{G_t}$$

$C_t$ is gamma mass from calls, $P_t$ is gamma mass from puts, and $G_t=C_t+P_t$. $I_t$ ranges from $-1$ to $+1$; a positive value means more curvature is in calls. This measures composition, not position sign.

6. Concentration index — gamma_mass_concentration_index

$$H_t=\sum_{(K,T)}\left(\frac{m_{K,T,t}}{G_t}\right)^{2}$$

This is the Herfindahl-Hirschman Index (HHI), a standard concentration measure. $m_{K,T,t}$ is gamma mass summed across contracts with strike $K$ and expiry $T$ on day $t$. $H_t$ is near zero when curvature is spread across many strike-expiry pairs and approaches 1 when it is concentrated in one pair. HHI is also used to measure industry concentration.

Across the 21 days, total gamma mass ranges from about 2.98 to 4.74 trillion. The near-spot share ranges from 0.191 to 0.316, and the concentration index from 0.0059 to 0.0293. Curvature is spread across the equivalent of dozens of strike-expiry pairs, never concentrated in one.

Why every factor except the first is a ratio

Total gamma mass rises mechanically with the price level through $S_t^2$ and with the size of the option market. The five ratios remove those scale effects, so they describe shape rather than size. In a one-month sample, a level factor can behave like a slow trend, making its rank correlation with another trending series misleading.

Trap

Here, "front expiry" means "expires today". SPY lists same-day expiries, and the cleaner drops only contracts whose expiry is before the trade date. The nearest expiry on day $t$ is therefore almost always day $t$. The front-expiry share equals the share of mass in same-day expiries on every sample day and averages 0.152. Those contracts end at the day-$t$ close, so about fifteen percent of the day-$t$ gamma picture cannot affect day $t+1$.

08Stage 4: the seven daily response metrics — metrics.py

def _build_daily_bar_metrics(minute_bars: pl.DataFrame) -> pl.DataFrame:
    """Compute realized variance and basic daily summary metrics."""

    daily_bars = minute_bars.with_columns(
        pl.col(CLOSE_COLUMN).log().alias("_log_close")
    )
    daily_bars = daily_bars.with_columns(
        (pl.col("_log_close") - pl.col("_log_close").shift(1))
        .over(TRADE_DATE_COLUMN)
        .alias(LOG_RETURN_COLUMN)
    )
    daily_metrics = daily_bars.group_by(TRADE_DATE_COLUMN).agg(
        pl.col(LOG_RETURN_COLUMN).pow(2).sum().alias(REALIZED_VARIANCE_COLUMN),
        ((pl.col(CLOSE_COLUMN).last() / pl.col(OPEN_COLUMN).first()) - 1.0)
        .abs()
        .alias(OPEN_TO_CLOSE_ABS_RETURN_COLUMN),
        pl.col(CLOSE_COLUMN).last().alias(CLOSE_PRICE_COLUMN),
        pl.col(VOLUME_COLUMN).sum().alias(TOTAL_VOLUME_COLUMN),
    )
    return daily_metrics.sort(TRADE_DATE_COLUMN)
In plain words

Turn about eight hundred price bars per day into measures of price movement, trading volume, and distance from yesterday's largest gamma strikes.

What it does

Input: minute bars for the full window. Output: one row per trade date with seven columns. Role: this is the response side of the research question: the outcomes tested against the gamma factors.

The formula — realized variance

$$RV_t=\sum_{k=2}^{n_t}\big(\ln C_{t,k}-\ln C_{t,k-1}\big)^{2}$$

$C_{t,k}$ is the closing price of minute bar $k$ on day $t$, and $n_t$ is the number of bars that day. The sum starts at $k=2$ because the first bar has no earlier bar on that day. This standard realized-variance estimator adds squared minute-by-minute log returns. It is not annualized: $4.3\times10^{-5}$ is daily variance, whose square root, $6.6\times10^{-3}$, is daily standard deviation of about 0.66 percent.

The formula — abnormal volume score

$$A_t=\frac{V_t}{\hat V_t},\qquad \hat V_t=\sum_{u}\ \frac{1}{w}\sum_{j=1}^{w} v_{t-j,\,u}$$

$V_t$ is total volume on day $t$. $u$ identifies a minute-of-day bucket, such as 09:31. $v_{s,u}$ is the volume in bucket $u$ on day $s$. $w$ is abnormal_volume_window, set to 20 trade dates. Expected volume $\hat V_t$ is therefore built minute by minute from the previous $w$ days. $A_t$ above 1 means the day traded more than its recent norm. Days without history get $A_t=0$ by contract.

The formula — pinning distance

$$\Pi_{t+1}=\min_{K\in\mathcal{K}_t}\ \frac{\big|C_{t+1}-K\big|}{C_{t+1}}$$

$\mathcal{K}_t$ is the set of five strikes with the most gamma mass on day $t$ (pinning_candidate_count). $C_{t+1}$ is the next trade date's closing price. $\Pi_{t+1}$ measures the distance from that close to the nearest large gamma strike, as a fraction of price. A small value is consistent with "pinning". Dividing by $C_{t+1}$ makes the measure comparable across price levels.

Why the volume baseline is built minute by minute

Intraday volume is usually highest at the open and close and lower in the middle of the day. A day missing its last hour of bars would therefore have lower total volume for a data reason, not a market reason. Comparing each minute with earlier observations for that same minute removes this daily pattern. The rolling mean is shifted one day inside each minute bucket, so day $t$ never uses its own volume.

Trap

min_samples=1 lets the rolling mean start with one observation. On day two, the "20-day baseline" is therefore just one prior day. The window never fills in this 21-day dataset, so every shipped abnormal-volume score uses a shorter and noisier baseline than the setting suggests.

The weakness, stated honestly

Realized variance uses every bar from 04:00 to 19:59 New York time, not only the 09:30 to 16:00 regular session. Thin pre-market returns therefore enter the sum with the same weight as regular-session returns. open_to_close_abs_return also uses the 04:00 bar as its open. The code has no session filter or setting for one.

Using only 09:30 to 16:00 makes realized variance smaller every day: the median ratio is 1.57 and the mean is 2.30. The two series have rank correlation 0.61 across 21 days, and on 2 January the extended-hours value is 9.6 times the regular-session value. The headline target therefore differs from a vendor's regular-session measure, and the session choice changes which days appear most volatile.

def _build_exposure_calendar(exposures: pl.DataFrame) -> pl.DataFrame:
    """Sort exposures and attach the next observed exposure date."""

    ordered_exposures = exposures.sort(TRADE_DATE_COLUMN)
    return ordered_exposures.with_columns(
        # The next exposure date defines the only allowed response match.
        pl.col(TRADE_DATE_COLUMN).shift(-1).alias(NEXT_EXPOSURE_DATE_COLUMN)
    )
In plain words

For each day, record the option surface at the close and attach the market's results from the next trading day. Keep that response date in the table so the pairing is easy to check.

What it does

Output: one row per exposure date with a following exposure date, containing six factors, the matched response_trade_date, and seven response columns with a next_day_ prefix. Role: the only place where a day-t variable meets a day-t+1 variable. Every downstream research module reads this table.

There are 21 exposure dates and 20 output rows. The last exposure date, 31 January, is dropped because no date follows it. The first response date, 2 January, is not used because no exposure date precedes it. That also removes the row whose abnormal-volume score is the placeholder zero.

Why the match is "next observed exposure date" and not "next calendar day"

Adding one day to Friday gives Saturday, which has no data. A calendar-date join would therefore drop every Friday. Shifting the exposure table by one row uses the next observed trading day instead. The matched date must also be the next exposure date. If the option file has a date missing from the bar file, the pair is dropped instead of reaching two days forward.

Where future data is excluded

Future data is excluded in three places. First, the response is strictly the following day, and response_trade_date remains in the output for checking. Second, the abnormal-volume baseline shifts its rolling mean one day inside each minute bucket. Third, each walk-forward model for row $j$ trains on slice(0, j) and predicts row $j$. All three match the data.

descriptive.build_quantile_summary — sort into buckets, average the target

def _build_quantile_buckets(row_count: int, quantiles: int) -> list[int]:
    """Assign each row to a deterministic integer bucket."""

    bucket_labels: list[int] = []
    for row_index in range(row_count):
        # Scale the zero-based row index into the integer bucket range
        # ``[0, quantiles - 1]`` without relying on percentile interpolation.
        bucket_index = (row_index * quantiles) // row_count
        bucket_labels.append(bucket_index)
    return bucket_labels
The formula

$$\text{bucket}(j)=\left\lfloor \frac{j\,q}{n}\right\rfloor,\qquad j=0,1,\dots,n-1$$

$j$ is the row's position after sorting by the factor, $n$ is the number of rows, $q$ is quantile_count. The floor brackets mean "round down to a whole number". With $n=20$ and $q=5$ this gives five buckets of exactly four rows.

Why rank position rather than percentile cut points

Percentile cut points must handle tied values, and libraries handle ties differently. That can change bucket sizes. Slicing the sorted rows by position keeps bucket sizes within one row of each other, which makes bootstrap results comparable. The trade-off is that bucket edges are not round factor values.

bootstrap.build_quantile_summary_with_ci — how wide is that number

The formula

$$\big[\hat\mu^{(\alpha/2)}_{b},\ \hat\mu^{(1-\alpha/2)}_{b}\big],\qquad \alpha=1-c$$

$c$ is bootstrap_confidence_level, 0.95, so $\alpha=0.05$. The procedure draws $n$ complete rows with replacement, sorts them into buckets, records each bucket's target mean, and repeats 1,000 times. $\hat\mu^{(p)}_{b}$ is the $p$-th percentile of the recorded means for bucket $b$. Resampling complete rows preserves the factor-target pairing.

Why the confidence bands are the same on every run

The generator uses a fixed seed: random_seed: int = 42 is the default argument of build_quantile_summary_with_ci(), and the pipeline does not override it. Re-running the pipeline therefore reproduces ci_lower and ci_upper to the last decimal. The seed is the only tunable value stored in source code instead of config.toml; changing it would move every interval slightly.

The weakness, stated honestly

The resample treats the 20 days as independent. Realized variance is strongly autocorrelated, meaning a volatile day is often followed by another volatile day. An independent-row bootstrap therefore understates uncertainty. A block bootstrap, which resamples consecutive runs of days, would produce wider bands. The bands above are the optimistic version, and they already overlap completely.

statistical_tests.build_statistical_test_summary — two formal tests

The formulas

Spearman rank correlation:

$$\rho=\mathrm{corr}\big(\mathrm{rank}(x),\ \mathrm{rank}(y)\big)$$

Kruskal-Wallis statistic:

$$H=\frac{12}{n(n+1)}\sum_{g=1}^{q}\frac{R_g^{2}}{n_g}-3(n+1)$$

For Spearman, $x$ is the factor and $y$ the target. $\mathrm{rank}$ replaces each value with its sorted position, so the measure detects a consistent increase or decrease, not only a straight-line relationship. $\rho$ ranges from $-1$ to $+1$. For Kruskal-Wallis, $n$ is total sample size, $q$ is the number of buckets, $n_g$ is the size of bucket $g$, and $R_g$ is the sum of the overall ranks of target values in bucket $g$. $H$ is large when buckets occupy different parts of the overall ranking. SciPy computes both tests using these formulas.

Sample data
out — statistical_tests.csv 
test_name                   test_statistic  p_value    sample_size
spearman_rank_correlation   0.030075        0.899837   20
kruskal_wallis              4.785714        0.309999   20

A p-value is the probability of seeing a statistic at least this extreme if there were no relationship. At 0.90 and 0.31, neither test finds evidence of one. This is the headline result for the shipped sample.

predictive — walk-forward forecasts

        # Train on rows strictly before the prediction row to keep the
        # evaluation out-of-sample and free from lookahead bias.
        train_frame = ordered_frame.slice(0, prediction_index)

The formula — what the ridge model minimises

$$\hat\beta=\arg\min_{\beta}\ \sum_{s=1}^{j}\big(y_s-\beta_0-\beta_1 x_s\big)^{2}+\lambda\beta_1^{2}$$

$x_s$ is the factor on training row $s$, $y_s$ is the target, $j$ is the index of the row being predicted, $\beta_0$ is the intercept, and $\beta_1$ is the slope. $\lambda$ is the penalty strength. Cross-validation chooses it from ridge_alpha_candidates when at least two folds fit; otherwise the first candidate is used. The term $\lambda\beta_1^{2}$ shrinks the slope toward zero and limits unstable fits from small early samples. Ordinary least squares uses the same expression with $\lambda=0$.

The formula — the two error measures

$$\mathrm{MAE}=\frac{1}{P}\sum_{p=1}^{P}\big|y_p-\hat y_p\big|,\qquad \mathrm{RMSE}=\sqrt{\frac{1}{P}\sum_{p=1}^{P}\big(y_p-\hat y_p\big)^{2}}$$

$P$ is the number of out-of-sample predictions, $y_p$ is the realized target, and $\hat y_p$ is the forecast. MAE is mean absolute error, the average size of a miss. RMSE is root mean squared error, which gives more weight to large misses. Both use the target's units, so for realized variance they are of order $10^{-5}$.

Why there is a naive baseline at all

The third model predicts that tomorrow's realized variance will equal the previous row's value. Volatility is persistent, so this is a meaningful baseline. A model that cannot beat it has shown little, even if its standalone error looks good. All three models use the same prediction dates.

This affects only the first walk-forward steps and never runs under the default configuration, but it matters if predictive_min_train_size changes.

13Fixes applied

Bug found and fixed: minute-of-day was wrapping around

In intraday/metrics.py, _build_minute_bars() computed the minute-of-day bucket as:

(pl.col(TIMESTAMP_COLUMN).dt.hour() * 60 + pl.col(TIMESTAMP_COLUMN).dt.minute())
.cast(pl.Int32)

Polars returns Int8 for both dt.hour() and dt.minute(). Int8 arithmetic wraps at 127. Because multiplication happened before the cast, hour * 60 overflowed from hour 3 onward. The result was not a valid minute-of-day value: 04:00 became −16, 09:00 became 28, 15:30 became −94, and 19:30 became −110. Different clock minutes also collided: 04:44 and 09:00 both mapped to 28. The 960 real minute buckets collapsed into 256.

The fix casts both parts to Int32 before arithmetic, names the 60-minute constant, and explains why in a comment:

(
    pl.col(TIMESTAMP_COLUMN).dt.hour().cast(pl.Int32) * MINUTES_PER_HOUR
    + pl.col(TIMESTAMP_COLUMN).dt.minute().cast(pl.Int32)
).alias(MINUTE_OF_DAY_COLUMN)

Blast radius: minute_of_day is used only by the abnormal-volume baseline. Since the trailing means are summed, merged buckets mostly cancel when every day has the same minutes. The largest change to abnormal_volume_score is therefore 0.0049, on 3 January, from 0.913192 to 0.918058. The column was still wrong and would be more wrong with missing bars or in an intraday volume plot.

Verification: after the fix, minute_of_day has 960 distinct values from 240 to 1199 (04:00 to 19:59). A regression test at tests/intraday/test_metrics.py::test_build_minute_bars_keeps_afternoon_minutes_distinct checks that 04:44, 09:00, 15:30, and 19:59 map to 284, 540, 930, and 1199.

Bug found and fixed: unusable rows were being filed into a real bucket

build_quantile_summary() in descriptive.py was the only public research helper without a cleaning pass. Its four siblings — statistical_tests, multi_factor, _build_spearman_summary_row, and the predictive helpers — first drop rows where either column is null or non-finite. This function sorted the raw table directly into buckets.

Polars sorts nulls first and NaN last. Because buckets use rank position, missing factors went into bucket 0, the "lowest gamma exposure" bucket, and NaN factors went into the top bucket. Their means were then reported as real readings. Three symptoms appeared on a small test table:

  • A phantom bucket. Two rows with a null factor and a target of 50.0 produced bucket 0, target_mean 50.0, observation_count 2. The lowest-exposure bucket was pure missingness.
  • A count that did not match its own mean. observation_count uses pl.len(), which counts every row in the bucket, while .mean() skips nulls. A bucket reported observation_count = 2 beside target_mean = null — two observations behind a mean that no row contributed to.
  • Two report tables disagreeing. On the same eight-row input, statistical_tests.csv reported sample_size 6 while quantile_summary.csv accounted for all eight rows.

The null mean also crashed the bootstrap. bootstrap.py wraps each resampled bucket mean in float(...) with a not-a-number default, but that default covers a missing key, not a key containing None:

float(resampled_means_by_bucket.get(bucket_label, float("nan")))
# TypeError: float() argument must be a string or a real number, not 'NoneType'

The fix applies the same pairwise cleaning before sorting:

clean_frame = frame.drop_nulls([factor_name, target_name]).filter(
    pl.col(factor_name).is_finite(),
    pl.col(target_name).is_finite(),
)

Blast radius: none on the shipped demo run. The alignment step removes the only day with missing values, so the 20-row research dataset has no nulls or NaN. Every output table remains numerically identical. The bug would have appeared on a longer or less complete sample as a crash and then as a false bottom bucket.

Verification: two regression tests were added to tests/research/test_descriptive.py: one checks that null and NaN rows never enter a bucket; the other checks that observation_count matches the rows behind target_mean. The suite now has 77 passing tests and 1 skipped.

Two more genuine defects, found but deliberately left alone

These are flagged rather than fixed because each fix requires an intent decision, and neither affects the shipped tables.

1. build_prediction_intervals() in predictive.py looks ahead. It builds one residual pool from the entire evaluation window and uses it for every row. The first out-of-sample interval is therefore informed by the last day's error. The module docstring says these helpers are walk-forward and date-sorted for time-series evaluation, but this function is not. On a test series with small residuals for twenty days followed by large residuals for twenty days, the first interval was roughly 800 times wider than an expanding-window interval. The exported and tested function is never called by offline_pipeline.py, so no shipped table is affected. A correct version would grow the residual pool one row at a time.

2. load_settings(project_root=...) does not relocate the config or environment file. The three path arguments are independent. Passing only project_root changes outputs_dir, but other settings still come from the real repository and the developer's real .env. Existing tests pass all three paths together, so they do not cover this case. Deriving the two file paths from the resolved root when omitted would fix it.

The pipeline is not bit-for-bit reproducible

Running gex run-offline-analysis twice with the same code and input does not produce byte-identical CSV files. Polars sums grouped floating-point columns across threads, and the reduction order varies, moving the last one or two digits. The measured drift is about $4\times10^{-14}$ relative in gamma_factors.csv and $1\times10^{-15}$ in intraday_metrics.csv.

The drift is far below the analysis precision, and every figure here is rounded beyond it. A byte comparison or checksum will still report a difference, so regression checks must use a numerical tolerance.

Also worth knowing

The committed tables under outputs/ and blog/data/ predate this fix, so their abnormal_volume_score column has the old values. They were left unchanged. Rerunning gex run-offline-analysis produces the corrected numbers.

Considered and deliberately not changed

Four choices could look like defects but would change every published number: the extended-hours session for realized variance, same-day expiries in the day-t gamma picture, the full-sample median for the regime cut, and the independent-row bootstrap for autocorrelated data. Three smaller issues remain: the ClickHouse client in raw_cache_builder.py is not explicitly closed, predictive.py keeps the unused forwarding alias add_naive_volatility_baseline, and its maximum cross-validation fold count is the bare number 5 instead of a named constant or configuration entry.

16Gotchas and traps

Idiom or settingWhat it doesRisk
dt.hour() in PolarsReturns the local hour of a timezone-aware timestampThe type is Int8. Arithmetic above 127 wraps silently. This is the section 13 bug; cast before multiplying.
expr.over("trade_date")Evaluates an expression inside each groupIt uses the table's existing row order, so sorting first is required. Both uses here sort first, and the resulting values are past-only.
rolling_mean(...).shift(1)Trailing average that excludes the current rowReversing the order to shift(1).rolling_mean(...) gives a different quantity. The regime module intentionally uses that order.
min_samples=1Produces a value after one observationEarly rows get a "20-day average" based on one day. The window never fills on a 21-day sample.
join(..., how="right") in _gamma_mass_share()Keeps dates with no contract in the bandAn inner join would delete those dates instead of assigning a zero share.
Same-day expiriesKept because the cleaner drops expiry only before trade dateAbout 15 percent of day-t gamma mass is in contracts that end at that close and cannot affect day t+1.
Extended-hours bars04:00 to 19:59 rather than 09:30 to 16:00Realized variance and open-to-close return include thin pre-market minutes. No session filter or setting exists.

robustness_band_widthsRe-tests bands 0.01, 0.03, 0.05The baseline 0.02 is absent, so the table does not show it beside its neighbours.

The notebook's hard-coded numbersSets the band, window, quantile count, and alphas directlyThese can drift from config.toml. The notebook uses 500 rather than 1,000 bootstrap iterations and four rather than five ridge penalties.

17Limitations, stated honestly

  • No position sign exists in the data. Everything here is unsigned gamma mass. The repository cannot distinguish dealers being long gamma from dealers being short gamma, even though that sign drives the usual gamma mechanism.
  • Twenty paired observations. This is one month of one symbol, with five buckets of four days. The sample is too small to detect a realistic effect reliably, so "no relationship found" says little about whether a relationship exists.
  • Three of fifteen output tables are empty by default, because two windows are as long as the sample. The code is working; the demonstration is short.
  • Association only. Even with more data, this design would show that two things move together, not that one causes the other.
  • Realized variance uses extended hours. This is not the standard vendor definition. Using 09:30 to 16:00 makes it smaller every day, with median ratio 1.57, and the two versions rank days only 0.61 alike.
  • The spot close is the 19:59 print, not the 16:00 official close. It differs on all 21 days, by up to 0.34 per cent. The five ratio factors are unchanged because scaling cancels, but the level factor moves by up to half a per cent and near-spot classification can flip at the band edge.
  • The confidence bands are optimistic, because the bootstrap treats consecutive trading days as independent.
  • The regime threshold uses the full sample. That is suitable for a descriptive split, not for a real-time classification.
  • Cleaning conventions move the answer. Non-positive open interest is 22 percent of the raw file, and same-day expiries are 15 percent of daily mass. Other defensible choices would produce different factors.
